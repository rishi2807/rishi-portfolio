Carina Editorial Components Framework

Lead Content Designer · Design system · 2023–2024

Cvent's design system had visual components but no content layer. Designers were writing their own microcopy, producing 40+ components with inconsistent labels, error messages, and empty states. I built the editorial framework that sat alongside the visual system — defining content patterns, writing rules, and reusable copy for every component type so the product could scale without content debt.

The problem

Cvent's design system, Carina, governed visual components — spacing, colour, interaction states. But there were no content standards attached to them. Every designer wrote their own button labels, error messages, and empty states. The result was a product that looked consistent but read inconsistently.

With 40+ components and multiple product squads shipping in parallel, the gap was growing faster than it could be manually corrected.

What I built

  • Content patterns for every major component type: buttons, form fields, modals, tooltips, banners, empty states, error messages, and confirmation dialogs.
  • Writing rules specific to each component — what goes in a button label vs. a tooltip vs. a modal heading, and why.
  • Error message framework: distinct patterns for validation errors, permission errors, network failures, and system errors, each with a template and worked examples.
  • Empty state framework: three categories (first use, no results, error) with content and illustration guidance for each.
  • Tone guidance by context: transactional surfaces vs. onboarding vs. destructive actions.

How it worked in practice

The framework was embedded directly in Figma alongside the visual components. Designers could see the content pattern while building — no separate document to find, no content designer to ask for every string.

It also gave content designers a reference when reviewing work. Instead of "I'd change this," the feedback became "this doesn't follow the error message pattern" — specific, system-backed, easier to action.

The impact

  • 40+ components documented with content patterns
  • Reduced back-and-forth between design and content in sprint reviews
  • Consistent error and empty state language across product areas that had previously diverged
  • Framework adopted as the standard for new components added after launch
